# ClaudeBridge 全项目审查与改进建议

> 审查基线：`5a24797`（Docs: explain reply detection after row pruning），包含实现提交 `d9bb75d`（Fix reply detection after virtualized row pruning）。审查日期：2026-10-12。
>
> 范围：HTTP 服务、协议适配、请求处理、浏览器驱动、页面池、DOM 适配、回复提取、生成状态机、提示词与工具解析、会话状态、任务快照、配置、日志、指标、测试、文档与项目配置。依据当前本地代码和 Git 跟踪文件进行静态审查，不访问 GitHub。
>
> 验证基线：最近一次本地全量 `pytest -q` 通过，2 项跳过；`git diff --check` 无错误。此次审查未重新运行 Ruff，也未在本轮审查中完成真实 Claude 页面及真实客户端的 E2E 验证。下文将静态代码可确认的问题与需要现场验证的假设分别说明。

## 1. 总体结论

项目的基本分层是合理的：

- `server.py` 处理 HTTP、请求上下文和错误映射。
- `api/*` 负责 Chat Completions、SSE 与 Responses 协议转换。
- `service.py` 协调会话锁、会话准备、生成、任务快照和指标。
- `completion/*` 负责浏览器会话生命周期、回复提取和生成状态机。
- `browser/*` 与 `driver.py` 隔离 DOM、选择器及浏览器生命周期。
- `session/*` 保存会话元数据，`tasks.py` 记录任务快照。
- `tests/` 覆盖主要协议、状态机、配置、安全和伪浏览器场景；真实浏览器用例单独放在 `tests/e2e/`。

总体设计方向正确：复用用户主动登录的浏览器会话，以 OpenAI 兼容层对外提供服务；不声称是官方 API，不自动绕过站点安全挑战，并明确将流式输出定义为从网页快照生成的合成流。

目前最主要的风险不是缺少更多功能，而是现有功能之间的状态与生命周期契约还不够严密。需要优先处理：

1. 工具说明注入可能被历史消息误抑制。
2. 管理操作可能与正在生成的请求相互打断。
3. 增量续写没有充分验证客户端历史与网页上下文是否一致。
4. 页面池、驱动初始化、回收和取消语义缺少完整的并发闭环。
5. 绝对超时、截断、流式错误和 Responses 事件语义需要统一。
6. 会话持久化、任务快照和配置行为仍有可靠性、隐私及运维风险。
7. 指标、配置和状态字段存在未接线的契约漂移。

不建议立即大规模重构。更稳妥的办法是按故障影响分阶段修复，每个行为变化单独配回归测试、单独提交，并保持真实浏览器验证独立于离线单元测试。

## 2. 已有改进与必须保留的设计

### 2.1 近期回复识别修复

提交 `d9bb75d` 已将新回复识别扩展为两条独立路径：assistant 节点数量增加，或本轮 user 消息指纹已变化且其后存在 assistant 节点。第二条路径不再依赖节点数量一定增加，能够覆盖页面回收旧行、虚拟化渲染窗口等情况。对应回归测试覆盖数量不变、数量下降、没有新提示词和缺少可比较节点等情形。

这是正确的修复方向，应该保留两路判定及对旧页面的保守兼容。不过它仍有一个需要验证的边界：如果连续两轮提交完全相同的提示词，且页面虚拟化后数量没有增加甚至下降，单靠文本尾部指纹无法区分两轮。后续应优先寻找稳定的 DOM 消息 ID、节点身份或可验证的消息元数据；若只能比较文本，应增加相同提示词的回归场景，并明确不确定时的退化策略。

### 2.2 生成结束判断采用时长

`end_detection.py` 将结束、停滞及提交未生效判定建立在秒数上，而不是轮询次数。这避免了调整轮询间隔时无意缩短停滞保护。应继续把纯函数状态机和虚拟时钟测试作为修改生成逻辑的主要安全网。

### 2.3 其他值得保留的措施

- 工具调用默认缓冲后解析，避免把中间标记泄漏到普通正文。
- 页面额度弹窗有独立识别、关闭和错误归因路径。
- 诊断接口有不返回正文的设计目标。
- 会话绑定 URL 已有 HTTPS、主机和路径检查的设计。
- 浏览器依赖惰性导入，离线测试可以通过替身运行。
- Responses API 默认关闭，不把未经验证的协议子集伪装为完整支持。
- 项目用配置漂移测试约束 `.env.example`、配置代码和 README。

## 3. P0：优先消除的正确性与安全风险

### 3.1 工具调用说明判重范围过宽

**涉及：** `claude_web/prompting.py`、`tests/test_prompting.py`。

现有 `_mentions_tool_instructions` 会扫描非 system 消息来决定是否重新注入工具说明。tool 结果或 assistant 历史只要包含 `[Tool Calling Instructions]` 这一普通文本，就可能被误判为用户已经在 system 层提供了完整工具说明。开发 agent 读取本项目工具代码、测试或文档时，很容易在历史内容中出现这个标题。

影响是提示词行为依赖偶然出现的历史字串：正常运行时工具能力可能被静默抑制；换新网页会话、重新播种后问题更明显，最终可能生成不符合工具协议的正文或错误格式。

**建议：**

1. 只在适当的 system / user 消息中查找显式内联说明，不扫描 tool 输出和 assistant 历史。
2. 要求标记位于行首并满足明确边界，避免普通引用、代码块或项目文档触发。
3. 更可靠的长期方案是记录本轮实际发送的工具说明版本或工具清单摘要；以协议状态而非任意文本推断是否已注入。
4. 增加回归测试：tool 结果、assistant 历史、代码块中包含该标题仍须正常注入；system 中确有说明时不重复注入。

### 3.2 管理操作必须与在途生成协调桶锁

**涉及：** `server.py`、`bridge_commands.py`、`service.py`、`completion/lifecycle.py`、相关管理命令与会话测试。

reset、link、unlink 以及会影响页面的 modal 操作必须与正在生成的任务协调，避免在生成期间关闭页面或导航到另一条会话，导致原请求提交失败、回复丢失或超时。

**建议：**

1. 在 `ChatService` 增加统一的管理操作入口，取得桶锁后再执行 reset / link / unlink / modal。
2. 对正在使用的桶采用短超时并返回明确的 `session_busy`，不要强行关闭其页面。
3. HTTP 管理端点、Chat Completions 聊天命令和 Responses 路径复用同一实现，避免重复维护管理操作逻辑。
4. 增加并发测试：桶忙碌时 reset/link 不得破坏在途任务；桶空闲时操作结果保持兼容。

### 3.3 增量续写缺少客户端历史与网页上下文的一致性校验

**涉及：** `completion/lifecycle.py`、`service.py`、`session/schema.py`、`tests/test_conversation_reuse.py`、`README.md`。

同一桶中，服务成功记录系统提示摘要和播种状态，之后只发送增量以减少重复提示词，这是合理的性能优化。但客户端请求的 `messages` 是客户端提供的完整历史，网页对话却是此前通过增量逐渐建立的历史。客户端可能清除历史、重新生成、压缩上下文、切换任务或改变 system/developer 指令。若只根据最后一条 assistant 之后的消息计算增量，而不验证历史前缀是否仍与网页会话一致，桥接层就可能把新任务接到旧任务的上下文后面。

这不仅是准确性问题，也可能成为跨任务上下文泄漏：UA 分桶默认启用时，同一客户端的不同任务可能共享桶，而不是独立上下文。

**建议：**

- 成功时保存客户端历史的稳定指纹：首条 user 摘要、消息序列指纹、末条 assistant 指纹、系统提示摘要和工具清单摘要。
- 下一轮先校验已有历史是否为当前历史的有效前缀；对不上时先只记录诊断，再开启新会话完整播种，最终切换行为须由回归测试保护。
- 系统提示、工具清单或对话历史发生重大变化时，默认重新播种，而不是把新规则附加在旧上下文末尾。
- 对不能判断的状态标记为不确定，禁止盲目重放可能已经提交的增量。
- 在 README 说明：多任务、多项目或有隔离要求时，应显式使用 `X-Claude-Session`；不要把 UA 桶当作用户或任务隔离保证。

## 4. P1：可靠性、并发和资源生命周期

### 4.1 浏览器启动、页面池和回收缺乏完整的并发闭环

**涉及：** `driver.py`、`page_pool.py`、`service.py`、`server.py`、`tests/test_browser.py`。

`ClaudeWebDriver.start()` 的幂等检查本身不能阻止两个协程同时观察到未启动，然后重复初始化 Playwright 或 Chrome。`PagePool.acquire()` 也存在类似窗口：查找页面后等待 `factory()` 创建页面时，另一个协程可能为同一个桶创建第二个页面；同时执行的逐出逻辑也可能超过页面数上限。

页面池有 `busy` 标记和空闲回收接口，但需要确认其是否从请求生命周期被正确调用，以及 lifespan 是否启动了周期回收任务。若忙碌标记没有接入实际生成链路，LRU 可能关闭正在使用的页面；反过来，如果没有周期任务，空闲 TTL 就只是一个声明而已。

**建议：**

- 给浏览器启动加共享 `asyncio.Lock`，确保多个桶首次并发请求只初始化一次。
- 给页面创建和池容量变更加同步机制；按桶合并创建任务，避免重复页面和资源泄漏。
- `ChatService._run_locked` 在取得页面使用权后设置 busy，在 `finally` 中释放；取消、异常和成功路径都必须复位。
- lifespan 启动周期 `reap_idle` 任务，关闭时取消并等待结束。
- 页面池满且所有候选都忙碌时，返回明确 busy，不要驱逐正在工作的页面，也不要默默超过容量。
- 对 readiness 使用独立且受控的探测路径，避免与生成请求并发操纵默认桶页面。
- 加入并发测试：浏览器只启动一次、同桶只创建一个页面、页面池不超限、忙碌页面不可被淘汰、空闲 TTL 确实回收资源。

### 4.2 会话锁管理与页面池的资源上限语义需要统一

**涉及：** `session/lock.py`、`page_pool.py`、`config.py`。

桶锁管理器与页面池各自拥有容量约束，但它们代表不同资源：会话桶锁的数量、页面数量、会话状态缓存条数不应被混为一谈。若桶锁层达到上限时只尝试驱逐空闲锁，但没有明确处理仍满载且无法驱逐的情况，就可能继续建立新锁并突破上限。页面池在相似情况下则需要决定返回 busy 还是拒绝创建。

**建议：**统一定义资源容量、淘汰候选、忙碌状态和满载错误语义；分别监测活跃桶、页面池占用、被拒绝请求和回收数。客户端可控的 `X-Claude-Session` 值还应限制增长速率，避免通过大量不同桶名制造资源压力。

### 4.3 取消与客户端断连的语义不完整

**涉及：** `completion/generator.py`、`service.py`、`server.py`、`errors.py`。

生成器的 `_fill` 使用 `except BaseException` 进行重试，会将 `asyncio.CancelledError` 等取消信号一起捕获，破坏协程取消语义。取消又不应该简单地视为普通生成停滞：它并不代表上游故障，不应被计入普通超时统计或无条件写入 `last_error`。

此外，非流式与 Responses 请求也需要明确处理客户端提前断开。客户端已经离开时，浏览器任务可能仍持有桶锁运行很久。取消任务还不等于页面已经停止生成；下一轮提交可能撞上正在工作的页面，导致 Enter 不生效或误判提交失败。

**建议：**

1. `_fill` 只捕获 `Exception`，不要吞掉协程取消。
2. 引入明确的取消错误或独立状态，在任务快照与指标中区分用户取消、客户端断连、上游超时和真实故障。
3. 为各响应路径建立统一取消令牌；在合适的时机检测客户端断连并传播取消。
4. 在提交前检测页面是否仍在生成；优先短暂等待，必要时只点击经过确认的停止控件，然后重新确认页面已可提交。
5. 对提交之后取消的任务保留状态不确定标记，不假设浏览器没有接收到提示词，也不要无条件重发。
6. 测试取消之后桶锁释放、页面状态清理、失败统计不被污染，以及取消后立即发送下一轮的情况。

### 4.4 提交之后的恢复与重复提交必须有明确状态机

提交前重新填入提示词通常可以安全重试；提交成功或可能成功后则不能同样处理。页面更新延迟、客户端取消、生成器异常或者回复节点暂时消失时，提示词可能已经写入网页会话。如果下一请求把同样的增量再次提交，就会重复执行用户操作。

**建议：**把一次生成记录为 `preparing`、`submitted`、`generating`、`completed`、`failed`、`cancelled` 或 `uncertain` 等明确状态。尤其应区分提交失败前的安全重试与提交后的不确定恢复。恢复前优先读页面现状并比对任务/消息指纹；无法判断时返回清楚的错误，而不是默默再发送一次。

### 4.5 绝对超时、延长额度和被截断回复的语义需要一致

**涉及：** `end_detection.py`、`completion/generator.py`、`api/chat_adapter.py`、`tests/test_end_detection.py`、`tests/test_generation_latency.py`。

生成器既有绝对超时，也有额外延长额度。必须仔细核对 `evaluate_poll` 的分支次序，特别是到达 deadline 且已有部分正文、页面仍在生成的情形。若该分支优先结束，延长配置就不能达到其预期作用，并可能把页面仍在继续生成的回复作为正常 `stop` 返回。

同时，超时到达时若返回已有正文，应区分这是完整回答还是被截断的部分结果；不能只为了兼容客户端而用正常结束语义掩盖截断。

**建议：**

- 使用虚拟时钟验证到期但仍在生成且已有正文、延长额度耗尽、到期前已经静止三个场景。
- 页面确实仍在生成并且还有延长预算时，先按策略延长；已达到硬上限时才结束。
- 对硬上限导致的截断使用兼容客户端的长度终止语义（如支持时使用 `finish_reason=length`），并在 notes 或错误元数据中说明。
- 如果超时前已经可靠落定，不应因额外延长预算而继续等待。
- README 应明确超时上限、延长额度和客户端能收到的结束语义。

### 4.6 Responses API 子集的流式行为与事件契约还需加强

**涉及：** `api/responses_adapter.py`、`server.py`、`tests/test_responses.py`。

此接口默认关闭是正确的保护措施。现有实现声明只支持一部分输入、输出及事件，不能按完整 Responses API 宣传。审查重点是：流式路径是否真正随生成增量发送事件，长时间无输出时是否有保活，客户端断开后是否取消生成，以及开始发送 SSE 之后发生的错误是否能够转成流内错误事件。

如果先 `await service.run()` 完整生成，再一次性输出 delta 事件，客户端看到的只是延后发送的合成事件序列，不是实际的增量流，且可能触发连接空闲超时。还应检查响应状态存储是否保留工具调用及工具结果的关联信息；只存 `role` 和 `content` 会让多轮 function call 链条丢失。

**建议：**

- 只有在功能真正支持时才启用端点，并在文档中逐项列出支持和不支持字段。
- 统一 chat 与 Responses 的队列、保活、断连、取消和流内错误策略。
- 按协议要求核验 `response.created`、输出项目开始/结束、正文 delta/done、工具参数 delta、完成和错误事件的顺序。
- `previous_response_id` 必须关联桥接层响应状态，并保留 assistant `tool_calls`、`tool_call_id` 与工具返回之间的关系。
- 通过目标真实客户端执行工具调用往返及长响应流测试，再决定扩大支持范围；不能只依靠宽松的自定义测试。

### 4.7 错误分类、重试边界与额度归因

**涉及：** `errors.py`、`server.py`、`service.py`、`completion/generator.py`、`browser/dom_adapter.py`。

需要避免三类混淆：把内部程序错误当成浏览器未就绪；在底层和上层叠加重试；以及仅仅因为提交前曾出现额度弹窗，就将后续任何生成失败都归为额度耗尽。

未处理异常不应该一律映射为 503 `NotReadyError`。这会误导客户端反复重试实际无法靠重试恢复的内部 bug。输入区填充本身已经有重试机制时，上层再次无差别重试还会放大次数；对于登录状态失效、选择器不存在等错误重复尝试通常没有价值。

**建议：**

- 新增内部错误类别，未预期异常返回语义清楚的 500，并在客户端响应中隐藏堆栈及敏感页面信息。
- 建立明确的可重试错误白名单；区分提交前的填充重试与提交后的禁止盲目重放。
- 只有当前弹窗仍然存在，或已经确认本轮未产生回复等足够证据时才归因 `usage_limit_reached`；已有有效正文之后的停滞不能仅根据旧弹窗命中归为额度错误。
- 为提交失败、回复提取失败、额度限制、上下文限制、浏览器不可用和取消提供独立指标。
- 错误详情只携带必要计数、选择器结果类别和状态，不返回 Cookie、提示词或完整 DOM。

## 5. P1：会话、持久化、配置与可观测性

### 5.1 会话绑定及 URL 相等判断应采用结构化比较

**涉及：** `completion/lifecycle.py`、`session/store.py`、`tests/test_conversation_reuse.py`。

当前设计需要精确区分目标会话和当前会话。基于 URL 字符串前缀或部分 ID 前缀的比较不够安全：两条不同会话的 ID 如果只在末尾不同，可能被错误判为同一会话。应统一解析 URL，校验协议、主机、路径及完整会话 ID。

还需明确 reset 语义：目前 `SessionStore.reset()` 新建状态时没有保留 `linked_url`。这意味着重置可能同时解除绑定，但 API 或聊天命令如果没有告知用户，就会使下次请求悄悄跳到另一条会话。

**建议：**

- 用 URL 解析器统一校验会话路径并精确比较完整 ID。
- 将 reset 定义为清除对话历史但保留绑定；真正解除绑定只由 unlink 执行，除非产品有相反且明确记录的语义。
- 对绑定会话达到上下文上限的情况提供明确处理，不要重复进入同一条已经无法继续的会话。
- 对服务重启和页面被回收后的恢复策略作清楚约定，并补充绑定、解绑、reset、seed 和 URL 边界测试。

### 5.2 会话状态文件存在读改写原子性问题

**涉及：** `session/store.py`、`session/lock.py`、`tests/test_sessions.py`。

`STATE_FILE_LOCK` 能保护单次文件读取或写入，但一次 `save_state()` 涉及读取整个文档、修改某个桶，再整体写回。若读和写之间没有覆盖整个读改写事务的同一把锁，并且多个调用同时更新不同桶，就可能发生最后写入覆盖先前更新的问题。固定 `.tmp` 文件名也需要考虑并发写入。

此外，`state()` 返回缓存中的可变对象，调用方直接修改后如果没有 `save_state()` 就只改了内存。写盘错误当前以日志警告为主，调用方可能不知道持久化失败，重启后状态会回退。

**建议：**

- 将读取、变更和写入统一为受锁保护的事务，或者用集中化的 `update()` 接口执行所有修改。
- 使用唯一临时文件并原子替换；区分写盘失败与成功，避免将未持久化的状态报告为已保存。
- 确认读写锁是进程内还是跨进程；明确不支持多 worker 时，在文档和启动检查中写出限制。
- 避免返回可被外部静默修改的缓存对象；考虑不可变快照或显式字段更新。
- 对同时更新不同桶、损坏文件恢复、迁移和写盘失败增加测试。

### 5.3 任务快照可能落盘敏感内容

**涉及：** `tasks.py`、`config.py`、`README.md`、`.gitignore`。

任务快照保存的 `last_reply` 是完整回复明文，`goal` 也可能包含用户消息摘要。即使文件被 Git 忽略，本地磁盘上仍可能长期留下业务内容、代码或敏感信息。诊断接口不返回正文，并不能消除本地落盘的隐私风险。

**建议：**

- 提供默认不持久化正文的选项，或只保存长度、摘要与错误类别。
- 如确实需要保存正文，应提供显式开关、保留期限和清理机制，并在 README 中说明存储位置与隐私影响。
- 确保临时文件、备份、日志、任务快照及浏览器 profile 的忽略规则一致；不要把登录资料或对话正文写入普通诊断日志。

### 5.4 路径与环境配置契约

**涉及：** `config.py`、`.env.example`、`README.md`、`tests/test_config.py`、`tests/test_config_drift.py`。

`USER_DATA_DIR`、`SESSION_FILE`、`TASK_FILE_DIR`、`OUTPUT_DIR` 等相对路径如果直接按当前工作目录解析，用户从不同目录启动服务时可能读写另一份登录 profile 或状态文件，导致登录丢失、状态分裂和难以复现的问题。

`env_list()` 同时将 `||` 和逗号当作列表分隔符，可能破坏含逗号的 CSS 选择器，例如 `:is(a,b)` 或合法选择器组。选择器列表配置应有单一、不歧义的分隔规则。

此外，宽松的主机白名单（例如 `LINK_ALLOWED_HOSTS=*`）会扩大持久化登录浏览器允许导航的范围；旧配置键被静默忽略也不利于维护。多个时间参数如果彼此矛盾，服务应该尽早告警，而不是运行到请求失败才暴露问题。

**建议：**

1. 对相对路径统一以 `PROJECT_ROOT` 解析，同时允许显式绝对路径。
2. 选择器列表只使用 `||` 分隔，给 `env_list()` 和逗号选择器增加测试。
3. 对危险的通配主机白名单启动强告警，默认始终保持目标主机最小化。
4. 检测废弃键并输出告警；对时间阈值、容量上限、端口和重试次数执行启动期校验。
5. 输出不含密钥的有效配置摘要，帮助用户确认正在运行的真实配置。
6. 保持 `.env.example`、`config.py`、README 和漂移测试同步；不要只修改其中一个。

### 5.5 日志关联、隐私和流式上下文

**涉及：** `logging_setup.py`、`server.py`、`bridge_commands.py`。

流式响应的生成常发生在路由函数返回 `StreamingResponse` 之后，若请求上下文只包住路由调用阶段，生成过程中的日志可能缺少 `request_id` / `session_key`。排查长任务时，这会让同一请求的日志难以串联。

`X-Request-Id` 由客户端提供时还应限制字符集和长度，避免日志伪造与无上限字段污染。管理命令日志应统一脱敏，不应随意记录完整会话 URL、用户给出的命令内容或完整异常堆栈。

**建议：**

- 在 SSE 迭代器/生成器内显式恢复请求日志上下文，或采用能覆盖 ASGI 发送阶段的统一方案。
- 对 request ID 进行白名单与长度校验，非法值改用服务器生成的 ID。
- 日志只记录必要状态、错误码、耗时与计数，统一通过 `redact()` 处理链接等敏感字段。
- 为同一请求记录阶段性耗时，验证正常完成、超时、断连和异常的关联 ID 完整性。

### 5.6 指标应当表达真实发生的事件

**涉及：** `metrics.py`、`service.py`、`completion/generator.py`、`browser/*`。

指标注册表中存在多项已声明但没有实际增加或观测调用的计数与时延，包括重试、浏览器不可用、选择器命中失败、回复提取失败、恢复、工具解析失败及请求/提取时延。空缺指标在 `/metrics` 中显示为零，容易被误解为故障没有发生。

**建议：**

- 每个指标明确在哪个层、哪个终态分支上更新，避免不同模块重复计数。
- 至少接上请求总时延、排队等待、浏览器启动、回复提取、恢复、取消、选择器回退和回复重写指标。
- 对 `reply_not_found` 记录计数、基线、结构判定结果等低敏元数据；不要记录正文。
- 为所有指标增加测试，确保一次失败仅增加正确的计数；删除无法提供可靠语义的指标或字段。
- 若使用 Prometheus，先明确命名和标签基数，避免为任意用户桶名创建无限时序。

## 6. P1：协议、提示词和正文处理边界

### 6.1 SSE 必须反映真实的回复变化

**涉及：** `generator.py`、`server.py`、`api/chat_adapter.py`、`api/streaming_adapter.py`。

网页正文通过快照采集，不保证每次变化都是纯追加。生成器每次轮询都回调 `on_delta` 会把重复快照放进队列，增加内存与调度开销。若页面重写已输出的正文，桥接层无法撤回已经发送的文本；如果只停止后续增量但仍用正常 `stop` 结束，客户端会把不完整内容当作完整回答。

流式最后块还应明确处理 `stream_options.include_usage`，并在客户端断开、上游异常和浏览器状态丢失时采用一致的流内错误策略。

**建议：**

- 仅在归一化正文真实变化时执行增量回调。
- 明确区分追加、重写、短暂节点消失和提取失败；保存上次有效快照，避免短暂 DOM 抖动导致整轮失败。
- 对无法撤回的正文重写提供 `bridge_notes` 或其他可兼容的截断提示，并加计数指标。
- 支持声明的 usage 流式选项，或在请求中明确拒绝不支持的选项。
- 测试中文、emoji、多字节字符、代码块、换行、空增量、重写、断连和流内异常。

### 6.2 页面外壳清理不能误删真实正文

**涉及：** `completion/extractor.py`、`browser/dom_adapter.py`、`tests/test_extraction_chrome.py`。

DOM 中可能有可访问性标题、动作栏、时间戳和推广文字，需要从 assistant 正文中移除。文本兜底规则如果只靠正文前缀或末行的时间戳样式，会误删真实内容：用户的引用可能恰好以 `Claude said:` 开头，日志、表格或代码结尾也可能类似时间戳。

**建议：**优先依赖 DOM 中实际识别到的外壳节点进行剔除；仅当对应外壳存在时才启用相关文本兜底。保留公式、Markdown 表格、代码、以时间格式结尾的正文、引用以及重复段落回归测试。任何不确定的清理规则都应宁可不删正文，而不是猜测性截断。

### 6.3 工具调用需要更完整的结构校验

**涉及：** `toolcalls.py`、`prompting.py`、`models.py`、`tests/test_toolcalls.py`。

工具调用由提示词约定和解析器模拟，不能当作 Claude 网页本身提供的原生工具协议。解析器除了识别围栏和无围栏文本，还需要处理正文与调用标记混杂、半截 JSON、多次调用和异常格式。只确认参数是 JSON 对象，并不等于符合工具声明的 `required`、属性类型与额外属性约束。

**建议：**

- 将调用提取、参数解析、schema 校验和 OpenAI 数据模型转换拆分成独立步骤。
- 对无法解析或不符合 schema 的调用返回受控诊断，不要把损坏标记悄悄当作合法正文或可执行参数。
- 对 DSML、JSON 围栏、无围栏及 `tool_uses` 等已观察到的形态建立固定测试样本；未支持形态应明确报告。
- 对嵌套代码块、转义字符、嵌套对象、重复调用、半截 JSON、缺少 required 字段及类型不匹配增加参数化/随机化测试。
- 继续遵循最小权限原则：桥接层不得执行模型生成的任意 shell 命令，也不得凭解析到的函数名称自动授予执行能力。

### 6.4 `tool_choice` 和提示词预算应遵守接口契约

**涉及：** `prompting.py`、`api/chat_adapter.py`、`models.py`、`config.py`。

若 `tool_choice` 被解析到内部任务，但生成与提示词构造没有真正使用，那么客户端发送 `none`、`required` 或指定函数时，实际行为可能与请求相反。工具说明也可能在每轮增量续写中重复注入，快速消耗网页上下文预算。

**建议：**

- 至少实现 `tool_choice=none` 不注入工具调用提示；对 `required` 和指定函数明确限制候选调用。
- 对未实现或无法满足的工具选择行为，返回清晰错误，不要静默忽略。
- 记录已注入的工具清单摘要；在新会话播种、工具清单变化或明确的刷新策略触发时才重新注入大段说明。
- 系统提示截断必须在 notes 中可见；应在长度限制中优先保留关键规则，并测试尾部规则不会因静默截断而消失。
- 将环境说明设为部署可控内容，不要把只适用于特定编码场景的默认文案注入所有对话。

## 7. P2：未接线的功能、工程化和文档

### 7.1 清理空壳和配置漂移

已声明但需确认是否有生产调用方的项目包括：

- 多个重试、浏览器可用性、选择器、回复提取、会话恢复及工具解析失败指标。
- `STREAM_KEEPALIVE_S`、`TASK_KEEP_MESSAGES` 等配置。
- `SessionState.cap_failures`、`TaskSnapshot.messages` / `recoveries` 和 `queued` / `generating` / `recovering` 等状态字段。
- 若干模型支持、页面判活、异常分类辅助函数。
- `TaskStore.load / clear`、兼容门面 `session_store.py`，以及 `main.py` 与 `claude_api_server.py` 两个入口。

不要仅依据命名断言它们完全没有用途。先做全仓库引用检索，并区分仅被测试调用、仅被文档提到与真正的生产调用方，然后二选一：接上线并补测试，或删除实现、配置和文档中的过期描述。避免留下看起来有保护、实际不生效的空壳。

### 7.2 自动化质量门禁

当前项目配置了 pytest 和 Ruff，但没有看到 `.github/workflows` 下的自动化 CI。建议增加最小质量门禁：

1. 在受支持 Python 版本上安装开发依赖。
2. 执行 `ruff check .`。
3. 执行离线 `pytest -q`，默认不运行真实浏览器 E2E。
4. 独立提供手动触发的真实浏览器探测任务，避免 CI 自动操作真实登录 profile。
5. 记录 E2E 最后实际运行日期、目标浏览器、页面选择器版本与结果。

Ruff 目前的规则集有意保持较小，可以逐步增加 Bugbear、升级兼容性和简化规则；先修复当前基线问题，再扩大检查范围。`pyproject.toml` 注释、依赖声明与实际工具配置应一致。

### 7.3 依赖与包发布

`requirements.txt` 与 `pyproject.toml` 存在重复维护依赖的风险；前者缺少与后者一致的上下界。建议明确哪一个是依赖真源，提供锁定/可复现安装流程，并在 CI 中验证干净环境安装、导入与基础启动。

项目声明 Python `>=3.13`。放宽最低版本前应先确认依赖支持范围、实际运行环境和目标用户需求；不要仅凭源码看起来没有新语法就直接调整。浏览器版本与 Playwright 版本也应在 E2E 记录中关联起来。

### 7.4 文档层次与操作性

`README.md`、`doc/design.md`、`doc/tasks.md`、`doc/tasks_claude.md` 和既有 `doc/update_claude.md` 承担不同职责，但随着事故修复容易出现重复说明和过期任务。建议统一：

- README 只留安装、配置、安全限制、客户端接入和常见排障。
- 设计文档说明模块边界、状态机与协议约定。
- 改进评审记录发现的问题、证据、优先级和未验证假设。
- 任务清单负责执行顺序、每项文件范围与验收标准，完成后同步状态。
- 每次事故记录实际症状、日志证据、根因、修复提交和回归测试；不要把推测写成实测事实。

可在 README 增加 `prompt_submission_failed`、`generation_stalled`、`context_limit_reached`、`reply_not_found`、`challenge_required`、`usage_limit_reached` 等错误的症状—诊断—处理表，避免用户从长设计文档中搜索。

### 第一批：请求正确性与管理操作边界

## 9. 完成标准

整个项目达到可维护状态，至少应满足以下条件：

- 公开端点的错误状态、副作用和输入边界都有明确文档与测试。
- 同桶请求严格串行；管理操作不能破坏在途任务；跨桶并发受浏览器容量限制。
- 请求取消、超时、断连、页面丢失和提交结果不确定都有不同语义，不会盲目重复提交。
- 复用会话前校验历史一致性；系统提示和工具清单变化可被可靠识别。
- 页面节点数量不再是新回复的唯一证据；同时覆盖重复提示词与虚拟化边界。
- SSE 只发送真实变化，并明确处理截断、重写、错误与 usage 选项。
- Responses API 的宣称范围与真实客户端测试结果一致。
- 会话状态写入不会丢失并发更新；任务快照的敏感信息可控且有保留策略。
- 诊断信息不泄露提示词、回复、Cookie 或敏感链接；日志能用请求 ID 串联完整生命周期。
- 关键指标和配置均有真实调用方；无用字段要么实现，要么删除。
- 默认离线测试与 Ruff 通过；真实浏览器 E2E 的限制、日期和结果可追溯。

## 10. 需要真实环境确认的事项

下列事项不能仅靠静态阅读完全定论，应安排实际探测：

1. Claude 当前页面中消息节点的身份稳定性，以及连续完全相同提示词遇到虚拟化时的识别能力。
2. 不同浏览器通道、登录 profile 和版本下生成状态信号、额度弹窗、页面回收及挑战页的真实行为。
3. 客户端断连后，浏览器能否停止生成并可靠恢复到下一轮可提交状态。
4. Responses SSE 事件是否满足实际目标客户端，而不仅是本项目对事件对象的断言。
5. 流式日志上下文在实际 ASGI 迭代阶段是否完整保留。
6. 多桶高并发、长任务、硬超时、额度上限和浏览器异常退出下的资源释放与恢复表现。

最终原则：把网页端不可控的 DOM 和生成时序视为外部系统，用可验证状态、保守恢复、明确失败语义和独立回归测试保护桥接层；不要以增加配置或日志字段代替真正的状态闭环。
