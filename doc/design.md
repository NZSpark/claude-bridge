# Claude Web-to-API Bridge 设计文档

将 Claude 网页版（`claude.ai`）包装为本地 OpenAI 兼容 API 服务，使 Pi Coding Agent、Codex CLI、OpenAI SDK 及其他兼容客户端能够通过 HTTP 调用已登录的 Claude 网页会话。

本文是设计方案，不包含实现代码。项目参考本地 `ChatGPTBridge` 和 `GeminiBridge` 的模块分层、会话隔离、任务快照、流式响应与测试策略，但针对 Claude 网页版重新设计页面交互、会话生命周期和模型选择。未经实际页面探测的 DOM 选择器、模型标签及交互细节均属于待验证项，不作为固定实现前提。

## 1. 目标、非目标与约束

### 1.1 目标

- 提供 OpenAI 兼容的 `GET /v1/models`、`POST /v1/chat/completions`。
- 在核心功能稳定后提供可配置的 `POST /v1/responses`，支持常见 Codex CLI 等客户端使用的 Responses 协议子集。
- 支持流式与非流式输出。流式响应由浏览器回复快照增量生成 SSE，不宣称底层网页提供了真实 token 流。
- 通过 Playwright 控制持久化 Chromium，复用用户主动完成登录后的网页会话。
- 实现请求级错误映射、会话分桶、并发协调、浏览器恢复、健康检查和诊断能力。
- 通过提示词约定与结构化解析模拟 OpenAI function calling，使客户端能够识别工具请求，并在后续请求中提交工具执行结果。
- 优先保证消息顺序、会话隔离、回复完整性与失败可诊断性，而不是追求完整复刻官方 Anthropic API。

### 1.2 非目标

- 不将本项目描述成官方 Anthropic API，也不使用或假设存在可供本项目调用的官方 API Key。
- 不将未经公开支持的 Claude 内部网络接口作为首期依赖。浏览器交互通过 Playwright 和可观测的页面 UI 完成。
- 首期不承诺完整支持图片、音频、视频、文件附件、Artifacts、引用来源、扩展思考、所有模型专属参数或 Anthropic 原生工具协议。
- 不承诺准确的 token 消耗、计费、context window 和模型能力数据。没有可信来源时不伪造 usage。
- 不提供多租户隔离与公网生产服务保证。默认只监听本机回环地址。

### 1.3 关键设计原则

1. **协议与网页解耦**：OpenAI 请求、回复模型与浏览器 DOM 不互相依赖。
2. **单一会话所有权**：同一会话桶的页面状态由唯一任务顺序控制，禁止两个请求同时向同一输入框写入内容。
3. **从完整消息历史恢复**：优先利用 API 请求中提供的消息历史重建对话，不将浏览器当前页面内容视为唯一事实来源。
4. **不能确认成功就不报告成功**：提交请求、生成结束、工具调用解析、页面导航等关键步骤都要有可观察的判定条件。
5. **网页变化可诊断**：选择器集中管理并支持候选回退；页面结构变化应产生明确的上游错误和诊断信息。
6. **最小暴露**：登录资料、提示词、回复正文和页面 DOM 不应默认写入日志或对外诊断接口。

## 2. 总体架构

```text
Pi / Codex CLI / OpenAI SDK / 其他客户端
                  |
                  | HTTP + JSON / SSE
                  v
+--------------------------------------------------+
| FastAPI 服务                                     |
|                                                  |
| 路由、请求校验、可选鉴权、错误映射                |
| Chat Completions / Responses 协议适配             |
|                                                  |
| 会话分桶、任务队列、超时和取消                    |
| 消息归一化、提示词构建、工具调用解析              |
| SSE 增量编码、usage 与 finish_reason 映射         |
+--------------------------------------------------+
                  |
                  v
+--------------------------------------------------+
| Claude Bridge Core                               |
|                                                  |
| Task Lifecycle -> Session/Page Pool               |
| Prompt Builder -> Browser Input                  |
| Reply Extractor -> End Detection                 |
| Tool Call Parser -> Protocol Serializer           |
| Session Store -> Snapshot / Recovery              |
+--------------------------------------------------+
                  |
                  | Playwright
                  v
+--------------------------------------------------+
| Chromium 持久化上下文                            |
| claude.ai 页面、登录态、会话页面与 DOM             |
+--------------------------------------------------+
                  |
                  v
       Claude 网页版生成与展示结果
```

一次 Chat Completions 请求的主要链路：

1. 解析请求体和请求头，识别目标模型、会话桶、流式模式及工具配置。
2. 将消息归一化为内部统一格式，校验角色顺序与内容类型。
3. 获取对应会话锁，创建任务快照并确认浏览器及网页已就绪。
4. 根据会话策略打开新对话，或定位到允许继续使用的已绑定对话。
5. 将完整历史转换成 Claude 网页输入框可提交的文本或消息序列。
6. 通过页面 UI 提交提示词，等待回复出现并采集增长中的正文。
7. 检测生成完成；如启用了工具模式，先缓冲并解析结构化工具调用。
8. 转换为 OpenAI 兼容的 JSON 或 SSE，记录运行指标并释放会话锁。
9. 页面异常、超时或上下文丢失时按已完成的任务快照执行有限恢复；无法安全恢复时明确失败，不静默发送第二遍。

## 3. API 协议设计

### 3.1 首期端点

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/models` | 返回当前配置并允许使用的模型别名 |
| POST | `/v1/chat/completions` | OpenAI Chat Completions，非流式与 SSE 流式 |
| GET | `/healthz` | 基础健康状态 |
| GET | `/readiness` | 检查浏览器、登录状态和输入区是否满足处理请求的条件 |
| GET | `/metrics` | 请求计数、耗时、失败分类和恢复计数 |
| GET | `/diagnostics` | 汇总浏览器、会话桶、选择器和任务状态，不默认返回正文 |
| POST | `/session/reset` | 重置指定会话桶的对话状态 |
| POST | `/session/link` | 可选：将会话桶绑定到符合规则的 Claude 会话 URL |
| POST | `/session/unlink` | 解除会话绑定 |
| GET | `/debug/dom` | 可选诊断端点，仅在调试开关开启时注册或开放 |
| POST | `/v1/responses` | 后续阶段启用的 Responses API 兼容端点 |

`/v1/responses` 应由 `ENABLE_RESPONSES_API` 控制。只有实现了所需事件类型、结束语义、错误映射及工具调用映射后才应宣告可用；不支持的字段不得伪装成已实现的功能。

首期不默认提供 Anthropic Messages API 的 `/v1/messages`。如后续确有需求，可新增独立的 Anthropic 协议适配器，共用同一内部请求模型和浏览器执行引擎，避免协议规则散落在网页驱动层。

### 3.2 Chat Completions 请求

采用兼容 OpenAI SDK 的常见字段：

- `model`：桥接层公开的逻辑模型别名。
- `messages`：按原顺序提供的历史消息。
- `stream`：是否以 SSE 返回。
- `tools`、`tool_choice`：启用提示词约定和结构化工具调用解析。
- `user`：可作为会话分桶标识的可选值。
- `max_tokens`、`temperature` 等参数：根据浏览器能力决定是否支持、映射或仅用于桥接层预算管理；不应承诺它们与官方 API 完全一致。

请求模型应允许合理的未知字段，避免兼容客户端因为发送额外参数而直接收到 422。但关键字段仍需校验；不能识别或无法安全执行的内容类型应返回明确的错误。

`messages` 的 `system`、`developer`、`user`、`assistant` 和 `tool` 角色需要经过统一归一化。Claude 网页界面并不等同于 API 的独立 system 参数，因此 system/developer 内容在首期采用显式标记的提示词前缀注入，不声称具有 API 层原生 system 语义。

### 3.3 响应格式

非流式响应应具有标准的 completion 标识、创建时间、模型别名、choices、message 和 finish reason 等字段。

- 正常文本以 `message.content` 返回。
- 已确认的工具调用以 `message.tool_calls` 返回，并设置与工具调用协议相容的结束语义。
- `finish_reason` 只能表达桥接层能够确认的结束状态；不能区分的网页端终止原因不得伪造为精确的官方语义。
- `usage` 在无法读取真实 token 消耗时，可以省略、使用明确标注为估算的数据，或按照客户端兼容性需要返回保守值。全项目必须统一其约定。
- 对上游错误使用可预测的错误对象，包含可读消息、错误类型和错误码，不返回堆栈、Cookie 或完整页面内容。

### 3.4 Responses API 子集

第二阶段复用内部消息模型实现 Responses API 兼容层，包括输入归一化、输出文本事件、完成事件、错误事件和工具调用事件。对于 `previous_response_id`，应使用桥接层自己的持久化响应状态进行关联，不能把它解释为 Claude 网页会话 ID。

必须明确不支持的事件、输出项目和请求字段。只有通过针对目标客户端的协议测试后，才将其加入正式支持范围。

### 3.5 流式输出

网页 UI 的回复通常通过 DOM 更新被观察。桥接层轮询正文快照，比较新旧内容并输出增量 SSE；这属于合成流，而非上游 token 级流。

Chat Completions 流式协议要求：

1. 开始时输出 assistant role 对应的首块。
2. 将新增长的正文作为 `delta.content` 发出。
3. 保持 UTF-8、换行、代码块和非 ASCII 字符完整；不得按字节拆坏字符。
4. 正常结束时发出带正确 `finish_reason` 的最终块，并发送 `data: [DONE]`。
5. 浏览器超时、取消或页面丢失时记录失败原因。SSE 已经开始发送后，不能再将响应改写成普通 HTTP 错误状态，只能结束流并采用约定的流内错误或连接关闭语义。
6. 如果启用工具调用解析，默认先缓冲回复，再输出经过校验的工具调用结构，防止将内部调用标记泄漏到普通文本中。

首期可以用可配置轮询周期结合正文差异检测实现。应注意文本重写、引用折叠、代码块调整等会导致快照不再是简单前缀的情况；检测到无法可靠表达的变化时，应采用重置策略或缓冲输出，而不是重复发送错误内容。

## 4. 浏览器与 Claude 页面适配

### 4.1 浏览器生命周期

- 使用 Playwright 持久化 Chromium 上下文复用已登录状态。
- 用户首次运行时在有头浏览器中手动完成登录；登录资料保存在本地独立目录。
- 启动时执行 readiness 探测，区分浏览器不可用、页面不是 Claude、登录失效、验证挑战、输入区不可用等状态。
- 不因为浏览器初始化失败而必然让整个 HTTP 服务进程退出；允许健康检查和诊断端点启动，并通过 503 类响应报告尚不可用。
- 服务关闭时等待或取消在途任务、关闭页面及浏览器上下文，并按设计持久化必要的会话元数据。
- 无头模式作为配置选项，但不能预设一定可用。必须通过目标系统的实际验证确定支持程度，不通过伪装浏览器或绕过站点安全挑战保证可用性。

### 4.2 页面导航和新建对话

目标入口可配置，默认从 Claude 官方网站的普通用户界面进入。不能假设当前会话始终停留在固定 URL，也不能仅凭地址栏判断输入区已就绪。

建议将导航分为以下状态：

- `browser_started`：Chromium 已启动。
- `page_loaded`：目标站点页面已经加载。
- `authenticated`：根据可观察 UI 信号判断用户已经登录。
- `composer_ready`：输入区域可以交互。
- `conversation_ready`：新对话或指定会话已经进入可发送状态。
- `generating`：页面已经显示正在生成的状态。
- `completed`：正文稳定且网页不再显示生成中的可靠信号。

这些状态是桥接层的内部状态，不要求网页本身暴露同名字段。实际实现应结合多个独立信号，例如页面标题、URL、输入区、发送按钮、停止生成按钮和回复节点，减少对单一选择器的依赖。

### 4.3 DOM 选择器策略

所有页面定位逻辑集中在 `browser/selectors.py` 或等价模块中。每类目标维护候选选择器和回退顺序：

- 输入区域：文本输入框或可编辑区域。
- 发送动作：发送按钮、可访问性名称或明确的提交操作。
- 回复区域：当前 assistant 消息正文，不把用户消息或历史回答识别成新回复。
- 生成状态：停止按钮、生成提示或其他可验证的 UI 状态。
- 新建对话入口：新会话按钮或可验证的普通网页导航。
- 模型选择器：仅在实际页面探测确认后启用。

候选选择器需要由真实网页探测与 E2E 测试验证，不能把网上示例中的选择器直接作为长期契约。优先使用稳定的语义属性和可访问性信息，避免依赖容易随构建变化的 CSS 层级、随机类名或页面文本的偶然组合。

当所有选择器均失败时，应返回诸如 `composer_not_found` 或 `reply_extraction_failed` 的内部错误类型，并在诊断信息中列出选择器命中情况。除非调试模式开启，不能默认保存或打印包含会话正文的完整 DOM。

**挡路弹窗（额度用尽 / 升级提示）要主动关掉（2026-10-12 事故）。** 额度用尽后站点会弹出
`role="dialog"` 的「Upgrade to keep chatting / You hit your 5-hour message limit」对话框。它盖住
输入区并抢走焦点，于是提示词**写得进 DOM、Enter 却不生效**、回复也不出现——桥接先报
`prompt_submission_failed`（「提交未生效」），或静止满 `STALL_S` 后报 `generation_stalled`
（「生成停滞」），而真正的原因是额度没了。处理约定：

- 探测与点击分开：JS 只做「可见容器 + 命中配置文案」的判定，并在挑中的**关闭类**控件上打标记；
  Python 侧再用真实点击去关（`MODAL_PROBE_JS` + `MODAL_MARKER_ATTR`）。
- 只点关闭 / 先不用类控件（`MODAL_CLOSE_SELECTORS` / `MODAL_CLOSE_TEXT_PATTERNS`），
  **绝不**点升级、购买、订阅等任何按钮；关不掉时退化到 `Escape`，仍关不掉只记日志，
  不让「关不掉弹窗」本身变成请求失败。
- 触发点：提交前关一次（生成链路每轮），以及**即将判定失败时**再探一次（只做一次，与
  「会话到顶」扫描同一处）。另外提供 `/bridge modal` 手动入口。
- 归因：只要本轮见到过这个弹窗、且本轮确实没生成，就报 `usage_limit_reached`（HTTP 429）
  而不是停滞 / 提交失败——重试同一个请求没有意义，应等额度重置或升级。

### 4.4 输入和回复提取

输入层独立处理文本填充、焦点、发送以及提交结果确认。对超长提示词，应采用经过验证的输入方式并检查最终输入文本，而不是默认一次粘贴必然成功。

回复提取器仅提取当前任务新增的 assistant 回复。提交前记录可识别的最后一条消息或页面状态快照，提交后等待新的回复节点或原有回复的明确增长。页面上残留的上轮文本不能被当作本轮输出。

**新回复的判定不能只看 assistant 节点条数（2026-10-12 事故）。** 提交前记基线、提交后
`count > baseline` 就认回复——这个口径有个真实缺口：只要页面在渲染本轮回复的同时**回收 /
复用旧行**（条数停在基线上），`count <= baseline` 就永远成立，于是页面上明明已经有回答，
桥也会一路轮询到停滞，最后报 `reply_not_found`（用户看到的现象是「网页回了，桥说没识别到」）。

同一次事故的第二轮（2026-10-12 14:17）暴露了更强的形态：长会话里页面只保留**渲染窗口**，
提交后节点条数会**比基线更少**（日志现场：`assistant 6/基线 8，提问 5/基线 8`，页面确实
已经回答）。此时条数口径失灵，而「条数没变多就当作还是基线那一条」的旧判定会把整轮判死。

因此判定用**两把独立的钥匙**，任一成立就算有新回复：

1. **条数**：assistant 节点比基线多（原口径，正常轮次走这条）；
2. **结构**：页面上**最后一条提问已经不是基线那一条**（首选按**最后一条提问的文本指纹**
   比较，与条数无关：指纹变了，或 user 条数变多了），**且其后面已经出现 assistant 节点**。
   指纹口径不受条数增减影响，所以页面回收 / 复用行、**甚至虚拟化掉旧行导致条数不升反降**
   时依然认得出。指纹读不到时才退回「user 条数变多」的旧口径。

两把都不成立才算「还没有新回复」。为什么结构信号必须挂「本轮提问」：页面上始终存在一条
assistant 节点（上一轮的回复），只凭「有节点」会把**上一条回复**当成本轮输出返回给客户端。
指纹读不到时（旧页面 / 替身页面）退回只看条数，与改造前行为一致。
是否走结构信号会记在读取结果上（`ReplyRead.structural`）；一旦出现，日志里会明确写一行，
说明当时条数口径失灵了。失败详情也会带上现场：`reply_count` / `reply_baseline` /
`user_count` / `user_baseline` / `trailing_reply`（后者用于区分「页面根本没渲染回复节点」
与「渲染了但条数口径没认出来」），且全部只有计数，不含页面正文。

**回复节点不等于正文。** 真实页面（2026-10-12 用 CDP 逐节点核对）的 assistant 消息节点里，
除了模型正文还有四类**页面外壳**，直接读 `innerText` 会把它们一起交给客户端：

1. `h2.sr-only[aria-hidden="true"]`：无障碍标题，内容就是**整段正文**（形如
   `Claude responded: <整段正文>`）。这是「同一段正文出现两遍」的真实成因。
2. `div[role="toolbar"][data-testid="message-actions"]`：Copy / Read aloud / 点赞 / 重试。
3. `<time>13 minutes ago</time>` / `just now`：时间戳。
4. `div[data-testid="growth-inline-line"]`：推广行（`Claude works directly with your codebase`
   + Install 按钮）。

所以提取分两层：

* DOM 层（`COMPLETE_TEXT_JS` + `REPLY_CHROME_SELECTORS`）在克隆节点上**剔除**这些子树，
  与「移除动画类 / 强制样式」共用同一次读取。列表放配置里，改版后加选择器即可。
  根节点始终是整个克隆节点，**不要**改成「正向选择 `.prose` 正文容器」：那样两轮之间
  根节点会切换，快照不再是前缀增长，会被当成「内容被重写」而中断流式。
* 文本层（`extractor.strip_page_chrome`）做窄口径兜底：只剔除「最后一行且整行就是时间戳」
  与已知的无障碍标题前缀（含它带来的整段重复），其余正文一个字不改——因此正文里
  中间出现的 `just now`、或没有标题前缀的重复段落都不会被动。

结束检测不能只使用固定 sleep。应综合观察：

- 是否检测到新的 assistant 回复。
- 正文是否**持续一段时间**保持稳定（时长，而非轮询次数）。
- 页面是否仍处于生成状态。
- 是否出现可识别的上游错误或登录提示。
- 是否达到单轮绝对超时、停滞时长或空回复容忍上限。

「页面是否仍在生成」必须由**多个独立信号取并集**得出，不能只认单一选择器：

1. 消息级——最后一条回复节点自身的 ``data-is-streaming``（页面自述「这条写完了没」）；
2. 控件级——可见的停止按钮 / 全局流式标记。

两者都探不到时按「没有生成迹象」处理，只有探测本身**抛异常**才记为「未知」（``None``），
未知绝不等于「已结束」。

无增长 / 停滞计时只看**本轮观测**，不能被「曾经见过生成中」的闩锁关掉——否则一旦早期
出现过生成信号、随后页面却不再产生新回复，循环就会一路空等到绝对超时而客户端在页面
早已静止后仍持续等待（实测客户端一直等到 ``generation_timeout``）。也不应把「提交没生效」
混进同一条慢路径：若页面空闲、正文无新增，而输入区里**仍留着本轮提示词**，即是提交未生效
的强证据，应立即以 ``prompt_submission_failed`` 结束；输入区读不出来（``None``）时不得据此
下结论，退回完整停滞窗口。

**阈值一律是「时长」而不是「轮询次数」（2026-10 调整）。** 轮询次数把「等多久才算结束」
与「多久轮询一次」耦合在一起：为了减少尾部等待而缩短轮询间隔，会同时把停滞窗口等比
缩短；反之要降低 DOM 压力而放慢轮询，收尾就会变慢。现在由一个「页面静止时长」累加器
（``end_detection.IdleClock``：页面在生成或正文增长即归零）驱动全部判定：

* ``SETTLE_S``（默认 2.5s）：页面自述已结束且内容静默这么久 → 收尾；
* ``SETTLE_NO_SIGNAL_S``（默认 6s）：两路信号都探不到时的更保守兜底；
* ``SUBMIT_LOST_S`` / ``STALL_S``（默认 6s / 30s）：静止多久判「提交未生效」/「停滞」。

轮询间隔因此只决定「多快看到变化」：页面活跃时用 ``POLL_INTERVAL_ACTIVE_S``（默认 0.4s）
把增量尽快交给客户端，页面静止后回到 ``POLL_INTERVAL_S``（默认 1.5s），且当页面已静止、
只剩收尾等待时只睡到静默阈值那一刻，不再让收尾被轮询粒度拖长。

**「会话到顶」判定：只能支撑失败，不能推翻成功。** 该判定是在整页文本里找一句特征文案
（``CONTEXT_LIMIT_PATTERNS``），因此有两层必须成立：

1. **只在即将判定失败时扫一次**（不按轮询次数、也不在成功路径上扫）。把整页扫描吊在
   「每次请求都会命中一次」的位置上，意味着页面别处出现一句同样的字样就能把一次**成功**
   的请求变成错误，并把桶标成到顶（下一轮重新播种）——这是实测事故。收尾优先：页面已经
   自述结束、正文也静止达标时，不再因特征文案改判；真正到顶时页面不会给出「已落定 +
   正文完整」的信号，而是不再产生新回复，因此一定会在失败判定点被拦到。
   命中时用 ``context_limit_reached`` 代替泛化的 ``reply_not_found`` / ``generation_stalled``
   （并在失败前先计一条不含正文的收尾日志）。
2. **扫描前必须剔除会话内容**（助手回复、**用户消息**、会话列表）与输入区，清单与挑战页
   扫描共用（``config.conversation_exclude_selectors()``）。事故现场（2026-10-12，CDP 逐
   节点核对）：一个把本仓库 ``.env.example`` 里的
   ``CONTEXT_LIMIT_PATTERNS=context limit||conversation is too long||...`` 读进会话的任务，
   那句话同时出现在用户消息与助手回复里；旧实现只剔除助手回复，于是每个请求都误报
   ``context_limit_reached``（同类事故见 doc/cloudfare.md 3.4）。
   剔除实现必须是**在 body 克隆体上剪掉子树**再读文本：body 的 ``innerText`` 会跨元素
   重新规范化空白，子树自己的 ``innerText`` 往往不是它的子串，用「整页文本减子树文本」
   做字符串替换会**静默失败**（实测同一段文本出现两次时只剔掉一处，另一处继续命中）。
   扫描先做一次廉价的 ``includes`` 预判，没命中直接返回空串，连克隆都不做。

这些条件应有独立单元测试（``end_detection`` 是纯函数状态机，``IdleClock`` 可用假时钟驱动），
并允许按环境调节轮询间隔与各项时长阈值。链路等待时间可用 ``tools/bench_pipeline.py``
（离线、虚拟时钟）复测。

## 5. 消息与会话管理

### 5.1 会话分桶

每次请求按以下优先级选择会话桶：

1. `X-Claude-Session` 请求头，可通过 `SESSION_KEY_HEADER` 更名。
2. OpenAI 请求的 `user` 字段。
3. 可选的 User-Agent 客户端标识。
4. 默认桶。

桶键需要做字符过滤和长度限制。默认启用会话分桶并设置最大桶数，超额时使用可预测的 LRU 回收策略，但不能在存在在途任务时直接回收其页面。相同桶中的请求通过异步锁串行执行；不同桶在页面池与环境资源允许时可以并行运行。

必须避免只按消息文本进行分桶：同一个客户端后续各轮需要保持连续的桶标识。

### 5.2 默认对话策略：复用网页会话 + 首轮完整播种

OpenAI Chat Completions 请求通常包含完整的 `messages` 数组，而网页对话依赖当前页面上下文。默认策略是**每个桶维持在一条网页会话里续写**：

1. 将请求消息规范化为内部对话记录。
2. 桶上还没有历史（首次使用 / 刚 reset / 页面被换掉）时，才为本次任务打开干净的新对话。
3. 需要播种时，按原顺序把历史消息与当前用户消息转成 Claude 网页可理解的输入序列；已播种的桶只发**最后一条 assistant 之后的新增消息**（`delta_messages`）。
4. 将必要的 system/developer 提示词、历史轮次以及工具协议说明合并到受预算约束的上下文中；系统提示未变时不重复注入，变了（换任务 / 换工作目录）才重新带上。
5. 采集本轮回复并向客户端返回。
6. 保留必要任务快照、错误摘要和会话状态供恢复及诊断使用。

只在首轮播种的好处是后续每轮输入短、延迟低，网页端也不会因为重放整段历史而堆出一大串重复对话。代价是网页会话成为长期状态：进程重启、页面被回收、浏览器换了 profile 之后，网页端上下文已经不在，而状态文件里的 `has_history` 仍然是真——因此**播种标记不能只靠磁盘状态**，必须同时绑定到内存里的页面对象（`SessionLifecycle._seeded_page`）；页面对不上就重新播种。

首次播种仍然要清晰标记消息角色，限制输入大小，并保留任务目标及最近消息，不允许无提示地截断用户最后一条消息。

### 5.3 上下文预算

网页端上下文限制和 UI 行为并不一定与客户端申报的上下文窗口相同。桥接层需要设置独立的字符或估算 token 预算，包含：

- system/developer 前缀和安全协议约定。
- 历史 user/assistant 消息。
- 工具定义和工具调用结果。
- 当前用户任务及必要格式要求。

预算应可配置。截断策略要优先保留当前任务目标和最新轮次，并在诊断信息中表明是否发生裁剪。首期不承诺精确 token 计数，也不应在 `/v1/models` 中虚构巨大 context window。

### 5.4 会话绑定（可选）

完成基础链路后，可支持将某个桶绑定到用户明确提供的 Claude 会话 URL，以便在指定网页对话内继续工作。推荐设计：

- `/link <URL>`：绑定并校验导航落点。
- `/link <URL> --seed`：绑定后将完整消息历史播种到目标对话，仅在目标会话尚无对应历史时使用。
- `/unlink`：解除绑定，回到默认新建会话和完整历史播种模式。
- `/link`：查看当前绑定状态。

URL 校验必须限制为 HTTPS、预期官方主机及明确允许的会话路径，拒绝非会话页面、外部域名和不支持的分享链接。最终应检查导航后的实际 URL 和页面状态，不能把成功调用 `goto` 当成绑定成功。具体 Claude 会话路径形态需通过真实页面验证后确定，并配置为可调整规则。

如果使用会话绑定，应持久化最少量必要元数据，包括桶标识、规范化 URL、是否需要播种和状态版本。绝不能将登录 Cookie 或完整浏览器存储复制到普通会话 JSON 文件。

## 6. 工具调用模拟

Claude 网页输出并不会自动等于 OpenAI 的 `tool_calls` 数组。首期采用与客户端兼容的提示词约定：把客户端提供的工具名称、描述、参数 JSON Schema 和调用格式转换成提示词附加内容，要求模型在需要调用工具时输出专用结构化标记及 JSON 参数。

解析器负责：

1. 识别工具调用标记，同时避免将普通 Markdown 代码块或用户引用的文本误判为调用。除正式围栏外，还按可信度依次回退到 DSML 风格 XML、DSML `invoke/parameter` 结构、`json` 围栏、带 `tool_uses` 键的裸对象，以及**无围栏的 `tool_call` 标记 + 平衡 JSON**——网页 DOM 会把 ``` 渲染成 `<pre>`，这是实测会发生形态。宽容路径额外要求条目包含可用工具名，普通 JSON 不会被当成调用。
2. 解析 JSON 并校验参数形状。
3. 检查工具名是否属于当前请求允许的工具集合。
4. 生成合法的 OpenAI `tool_calls`，并为每次调用生成唯一 ID。
5. 在失败时记录可诊断原因；无效结构不能被静默转换成可执行命令。
6. 对未通过解析的标记采取明确策略：默认按普通文本返回或产生解析诊断，具体行为由协议兼容测试确定。

工具执行权属于调用客户端。桥接层首期只负责生成并回传工具调用，不因为收到模型输出就自行执行任意 Shell、文件访问、浏览器操作或其他本地命令。客户端下一轮通过 `tool` 消息发送执行结果时，再按照请求历史进行播种。

在工具模式下，建议缓冲整段模型回复后再解析和输出，以避免先向客户端泄漏工具标记、随后又无法撤回。非工具模式可以按正常文本流式传输。需要严格测试工具调用与正文混合、多个调用、畸形 JSON、未声明工具、部分流输出及工具结果轮次等边界场景。

## 8. 配置设计

环境变量与 `.env.example` 是配置契约。配置名称、默认值、说明、实际解析与测试需要保持一致；不能出现文档写了开关、运行代码却无法读取的情况。

建议配置项如下：

| 分类 | 配置项 | 设计说明 |
| --- | --- | --- |
| 监听 | `HOST` | 默认 `127.0.0.1` |
| 监听 | `PORT` | 选择不与本机其他 Bridge 冲突的默认端口，例如 `8003`；启动日志打印实际监听值 |

| 生成 | `SETTLE_NO_SIGNAL_S` | 探不到生成信号时的兜底静默时长 |

| 会话 | `BUCKET_LOCK_TIMEOUT_S` | 同桶等待超时，超时后返回可重试的忙碌错误 |
| 会话 | `BUCKET_IDLE_TTL_S` | 空闲页面回收时间 |
| 上下文 | `CLAUDE_MAX_CONTEXT_CHARS` | 上下文字符预算，首期优先采用可解释的字符预算 |
| API | `ENABLE_RESPONSES_API` | 是否注册 Responses API 路由 |
| API | `BRIDGE_TOKEN` | 可选的桥接服务 Bearer Token |
| 安全 | `RESET_TOKEN` | 可选的会话重置保护令牌 |
| 工具 | `TOOL_CALL_BUFFER` | 工具模式是否整段缓冲后再返回 |
| 调试 | `CLAUDE_DEBUG` | 控制调试日志和诊断路由 |
| 诊断 | `SAVE_DEBUG_ARTIFACTS` | 默认关闭；显式开启后仍必须脱敏并限制保存内容 |

默认监听回环地址。服务启动时应拒绝或醒目警告不安全的监听配置。`BRIDGE_TOKEN` 如果启用，则保护生成类 API 和可能改变状态的管理端点；不能只保护某一个协议端点。令牌校验应采用标准 Bearer 头，比较过程避免不必要的信息泄漏。

实际配置默认值的唯一事实来源应与配置模块一致。推荐通过 `tests/test_config_drift.py` 检查 `.env.example`、配置读取代码和本文约定，避免参数漂移。上表是设计建议，具体默认值应在实现时集中确定。

## 9. 错误处理与恢复

### 9.1 内部错误类别

建议最少包括：

- `browser_unavailable`：浏览器初始化或页面句柄不可用。
- `authentication_required`：网页要求登录。
- `challenge_required`：检测到安全挑战或无法继续的访问验证。
- `composer_not_found`：找不到可操作的输入区域。
- `prompt_submission_failed`：无法确认提示词已成功提交。
- `reply_not_found`：提交成功后未识别到本轮回复。
- `reply_extraction_failed`：回复结构无法可靠提取。
- `generation_timeout`：本轮超过绝对超时。
- `generation_stalled`：正文长时间没有有效增长且不能确认正常完成。
- `context_limit_reached`：观察到可识别的上下文限制提示。
- `usage_limit_reached`：网页账号额度已用尽（页面弹出升级 / 额度提示），本轮无法生成。
- `session_conflict`：绑定或页面状态与预期不一致。
- `session_busy`：桶锁等待超时。
- `tool_call_parse_error`：工具调用输出解析失败。
- `unsupported_input`：当前版本不支持的内容类型或参数。

### 9.2 HTTP 状态映射

| 情况 | 建议状态 | 说明 |
| --- | --- | --- |
| 请求结构无效 | 400 | 返回明确的参数问题 |
| 鉴权失败 | 401 / 403 | 仅在对应安全功能启用时使用 |
| 会话桶忙碌 | 503 | 可由客户端稍后重试 |
| 浏览器或登录状态未就绪 | 503 | 不应返回看似成功的空回复 |
| 网页发生无法恢复的结构或交互错误 | 502 | 作为上游网页执行错误 |
| 单轮生成超时 | 504 | 明确指出生成超时 |
| 未启用的 API 端点 | 404 | 与启动配置保持一致 |

状态码之外还应提供稳定的内部错误类型和安全的诊断消息。健康检查与 readiness 的语义需要区分：进程存活不意味着浏览器可以处理请求。

### 9.3 任务快照与安全重试

任务快照至少包含任务 ID、桶键、请求消息摘要或受保护的消息数据、目标模型、开始时间、当前状态、提交状态、最近一次回复快照和恢复次数。

推荐状态机：

`queued -> preparing -> submitted -> generating -> completed`

异常路径：

`preparing/submitted/generating -> recovering -> completed/failed`

在导航前或提交前失败时，可以在确认页面无副作用的条件下重新准备任务。提交操作一旦可能成功，而页面又丢失或状态不确定时，不得无条件重发，否则可能在网页中创建重复对话或重复回答。应先尝试重新附着、检查 URL 和页面状态、读取现有回复；只有确认未提交，或明确进入全新对话并安全重放完整任务后，才允许再次提交。

重试次数、退避间隔与恢复分支必须可配置、可测试。不能在每次请求失败时无限重试。

## 10. 安全与隐私

- 默认 `HOST=127.0.0.1`，不提供开放公网使用的默认配置。
- 浏览器登录态和本地资料视同账户凭据，不进入 Git、不包含在发布包或测试工件中。
- `.gitignore` 应排除 `.env`、浏览器用户目录、会话状态、日志、调试截图和输出文件。
- 可选 `BRIDGE_TOKEN` 保护生成接口；如果关闭鉴权，也必须在启动日志和 README 中明确说明本地网络边界。
- 不把完整提示词、回复、Cookie、令牌、浏览器存储或敏感 DOM 写入常规日志。
- `/diagnostics` 默认返回布尔状态、计数、耗时和错误类别，不返回原始网页正文。
- `/debug/dom` 只能在显式调试模式下启用，并需要限制访问范围和输出内容。
- 会话 URL 和桶键可能包含可关联用户的信息，日志中应脱敏或散列处理。
- 对会话绑定 URL 进行严格主机与路径校验，防止将持久化浏览器会话导航到任意网站。
- 只有声明且通过参数校验的工具调用可以被返回为 `tool_calls`；桥接层不默认执行模型生成的命令。
- 浏览器页面和模型输出都属于不可信输入；不能因为回复中包含貌似内部指令或 JSON 就提升其权限。

## 11. 测试策略

### 11.1 单元测试（默认不联网）

所有协议、状态机、提示词和解析器测试都应使用 Fake Driver、Fake Page 或明确的接口 mock，不依赖真实 Claude 账号。

- 配置解析、默认值、类型转换与配置漂移。
- 消息归一化、多角色拼接、内容类型和上下文预算。
- OpenAI 请求/响应模型及错误响应契约。
- 工具提示词、合法/非法 JSON、未声明工具名与多调用。
- SSE 首块、增量去重、终止块、`[DONE]` 及中断场景。
- 结束检测：正文增长、正文稳定、停止按钮状态变化、空回复、错误页及超时。
- 会话分桶优先级、键清洗、桶锁、LRU 与空闲回收。
- 任务快照持久化、状态迁移及提交不确定时的恢复策略。
- URL 绑定白名单、安全诊断、令牌校验和日志脱敏。
- Responses API 的请求与事件映射（如果对应阶段已实现）。

### 11.2 E2E 测试（显式开启）

真实网页测试必须通过类似 `CLAUDE_E2E=1` 的显式开关启用，默认测试套件不能触发外网请求或消费用户网页额度。运行前应检测浏览器、登录状态和必要环境配置。

核心场景：

1. 初始化浏览器并识别已登录、未登录及挑战页面。
2. 首次对话能提交短文本并读取完整回答。
3. 多轮历史播种后，模型能够基于前文回答。
4. 流式模式的最终合并文本与非流式结果结构一致。
5. 回复含 Markdown、长文本、换行和代码块时不会截断或重复。
6. 两个桶并发请求时，消息不会串线。
7. 同一桶连续请求时，任务顺序保持确定。
8. 生成超时、用户主动取消或浏览器页面丢失时返回正确错误。
9. 工具调用能转换成合法 `tool_calls`，且工具结果轮次不会污染其他桶。
10. 网页选择器变化时，诊断能指出具体缺失的交互元素。
11. 服务重启后能安全恢复配置及会话元数据，不泄漏认证资料。

真实测试需要使用用户授权的普通网页会话，遵守站点正常使用限制，并通过配置明确限制运行频率；不应通过反复发起高成本长回复来验证简单状态机逻辑。

## 12. 实施阶段

### 阶段 A：基础浏览器原型

- 选择并验证 Python、FastAPI 与 Playwright 依赖版本。
- 实现持久化浏览器启动、登录状态探测、目标页面导航和关闭流程。
- 验证输入框、发送动作、新回复定位和生成完成判定。
- 编写最小真实网页探测测试和 Fake Page 单元测试。
- 输出页面选择器验证记录与已知限制。

交付标准：能够在用户正常登录后，用明确的单条提示词完成一次提交并返回确定的新回复，不会把历史页面内容误识别为当前答案。

### 阶段 B：OpenAI Chat Completions

- 实现内部消息模型和请求校验。
- 实现提示词构建、完整历史播种和上下文预算。
- 实现非流式端点、模型列表及标准错误对象。
- 实现 SSE 合成流与结束状态机。
- 接入健康检查、readiness 和请求指标。

交付标准：常见 OpenAI SDK 非流式与流式调用均能工作；本地单元测试不依赖真实网络；生成失败不会被伪装成成功响应。

### 阶段 C：多会话与可靠性

- 实现请求桶优先级、异步桶锁、页面池及资源回收。
- 实现任务快照、超时、异常分类和安全恢复。
- 实现 session reset、可选绑定与 URL 落点校验。
- 实现日志脱敏、可选桥接鉴权与调试接口开关。

交付标准：并发隔离、页面丢失恢复和提交不确定时的处理有专门测试，不能出现静默重复提交。

### 阶段 D：工具调用与客户端兼容性

- 实现工具定义转换、结构化输出约定和严格解析。
- 覆盖多工具、畸形输出、工具结果轮次与流式缓冲。
- 用目标客户端进行端到端验证并记录支持的字段范围。

交付标准：无效工具结构不会变成有效调用；普通文本模式不泄漏内部协议标记；客户端确实能识别返回的工具调用。

### 阶段 E：Responses API 与完善文档

- 如果目标客户端需要，开发 Responses API 独立适配器。
- 完成事件、错误、工具调用和响应状态关联。
- 编写安装、首次登录、故障诊断和限制说明。
- 执行完整测试套件，并核对配置和文档的一致性。

交付标准：仅发布已经通过协议测试的功能，不宣称未验证的 Responses API 特性可用。

## 13. 验收标准

发布首个可用版本前必须满足：

- 服务只能通过配置显式改变监听边界，默认本地可访问。
- `/v1/models` 返回真实配置的逻辑别名，而不是虚构全部 Claude 型号。
- Chat Completions 支持基本 user/assistant 多轮文本请求、非流式与 SSE 流式输出。
- SSE 的最终拼接内容正确，正常结束有结束块与 `[DONE]`。
- system/developer、工具与历史消息经过明确的归一化规则处理。
- 多桶并发和同桶串行行为有单元测试覆盖。
- 页面异常、登录失效和生成超时可区分，不以空内容假装成功。
- 工具调用只有在输出格式与参数验证通过后才返回结构化调用对象。
- 默认测试不联网，不要求调用者提供真实登录态。
- 真实 E2E 需显式启用，并且不绕过网站安全机制。
- 调试接口、认证资料、提示词和用户回复遵守隐私与访问限制。
- `.env.example`、配置代码、README 和测试契约一致。

## 14. 主要技术风险与待验证事项

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| Claude 网页 DOM 改版 | 输入、回复提取或生成状态探测失效 | 选择器集中管理、候选回退、DOM 探测和 E2E 诊断 |
| 登录过期或安全挑战 | 浏览器无法继续生成 | readiness 明确报告，提示用户正常处理，不尝试绕过 |
| 网页生成停止信号不稳定 | 回复提前结束或等待超时 | 综合正文稳定性、停止按钮和时间阈值判断 |
| 历史播种提示词过长 | 延迟增加、上下文受限 | 字符预算、保留当前任务目标、报告截断情况 |
| 浏览器提交结果不确定 | 重试引起重复消息 | 记录提交阶段，先核对页面，不盲目重发 |
| 客户端期望真实 token 流 | 延迟或流式语义差异 | 明确合成流性质，测量首块时间与增量正确性 |
| 网页模型选项随订阅变化 | 模型别名与实际模型不匹配 | 通过配置映射 UI 可选项；未验证的映射不公开 |
| 网页不支持 API 原生参数 | 参数被忽略或语义偏差 | 文档公开支持矩阵，避免宣称与官方 API 等价 |
| 工具调用结构不稳定 | 无法解析或错误调用工具 | 工具模式缓冲、严格解析与声明集合校验 |
| 长时间运行资源增长 | 页面、上下文或会话状态膨胀 | 页面池上限、空闲回收、有限持久化及资源监控 |

### 首期明确决策

1. 首期优先实现 OpenAI Chat Completions，不同时实现多个协议入口来增加调试面。
2. 首期默认用完整历史播种建立独立任务上下文；稳定后再评估增量复用现有网页会话。
3. 所有 Claude 网页 DOM 选择器均以真实页面探测结果为准，本文不固化未验证的属性或 CSS 路径。
4. 工具调用先解析再返回；桥接进程默认不执行模型生成的工具或本地命令。
5. Responses API、会话绑定和扩展输入类型按阶段加入，并以测试结果决定是否对外宣告支持。
6. 服务默认仅供本机使用，不将浏览器登录态桥接成可直接暴露公网的无保护服务。

以上方案构成 ClaudeBridge 的初始技术设计。进入实现阶段后，应将真实网页探测结果、客户端协议测试和关键架构决策同步补充到 `doc/tasks.md` 与 `doc/e2e_test_design.md`，并确保文档描述与实际支持范围一致。
